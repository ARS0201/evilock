# PROJECT: EviLock

## Secure Digital Document Management and Evidence Integrity System

### 1. PROJECT OVERVIEW

Build a complete, responsive, professional full-stack web application named **EviLock**, based on Smart India Hackathon 2026 Problem Statement SIH26190: Secure Digital Document Management System for Legal and Investigation Documents.

**Tagline:** Protecting Evidence. Preserving Trust.

EviLock is a secure digital platform for storing, organizing, retrieving, verifying, and sharing sensitive legal and investigation documents.

The target users include:

* Police officers.
* Investigating officers.
* Legal officers and prosecutors.
* Court-authorized personnel.
* Forensic experts.
* System administrators.
* Authorized auditors.

The system must manage documents such as:

* FIRs and police reports.
* Investigation records.
* Witness statements.
* Charge sheets.
* Court filings.
* Evidence records.
* Forensic reports.
* Legal notices.
* Court judgments.
* Other authorized legal documents.

The application must address unauthorized access, document tampering, poor version control, fragmented document storage, inefficient collaboration, and a lack of traceable document activity.

Build a working application, not merely a static UI design. Implement a functional frontend, backend, database, authentication, authorization, document management, and audit functionality.

Do not fabricate successful operations or show simulated results as real security verification.

### 10. DOCUMENT VERSION CONTROL

Never silently overwrite a previous document version.

When an authorized user submits a correction:

1. Preserve the previous version.
2. Create a new version.
3. Calculate a new SHA-256 hash.
4. Record the uploader and timestamp.
5. Store the change description.
6. Create an integrity-ledger entry.
7. Record the event in the audit trail.

Display a version timeline.

Allow authorized users to retrieve previous versions.

For evidence records, use a controlled correction or superseding-record workflow.

Preserve original evidence bytes and prevent ordinary users from modifying historical versions.

### 11. INTEGRITY LEDGER AND BLOCKCHAIN

Create a dedicated page called "Integrity Ledger."

Use the EviLock brown theme throughout the interface.

For the initial prototype, implement an append-only, tamper-evident ledger.

Each entry must include:

* Entry ID.
* Document ID.
* Version ID.
* Document SHA-256 hash.
* Previous ledger-entry hash.
* Entry hash.
* Event type.
* Actor ID.
* Timestamp.

Calculate the ledger-entry hash from canonicalized entry data, including the previous-entry hash.

Implement a verification process that checks:

* Stored file hash.
* Original recorded hash.
* Ledger-entry integrity.
* Previous-entry hash relationships.
* Digital signatures where applicable.

Display these outcomes:

**VERIFIED:** The document hash matches its reference, and the required ledger checks pass.

**MISMATCH:** The document hash differs from its reference.

**LEDGER ERROR:** Ledger consistency checks failed.

**UNVERIFIABLE:** Required verification data or services are unavailable.

Provide a button labelled "Verify Integrity."

Show the result, timestamp, version, expected hash, actual hash, and verification details only to authorized users.

Record verification attempts in the audit trail.

Do not falsely claim that an ordinary database hash chain is a real blockchain.

Keep the architecture ready for integration with Hyperledger Fabric or another suitable permissioned blockchain.

A real blockchain integration must be separately configured, connected, and tested before being described as implemented.

Never store confidential document contents directly on a blockchain.
